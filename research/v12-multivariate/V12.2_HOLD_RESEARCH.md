# KINGBOT V12.2 — BTC data-depth and HOLD-aware loss research

This is a research-only follow-up to V12.1. It does not change production inference, Render services, broker integrations, customer accounts, secrets, or order execution.

## What V12.1 established

The completed V12.1 artifact showed 25/25 market feeds and zero hard fetch failures, but BTC used the Kraken OHLC fallback at only 719–720 candles while the FX/gold 1m series contained 2,499 candles. The BTC 1m series began at 2026-11-06T22:05:00Z, after the FX/gold 1m series ended at 2026-11-06T20:53:00Z, so those 1m series had no shared history window.

The strongest development deltas were Breakout/full-context (+0.01090 selection-score points) and Ladder-Flip/target-only (+0.01124). Neither passed all absolute development gates, so neither entered the untouched final window. All V12.1 specialists remain research-rejected.

## V12.2 data-depth repair

The V12.2 fetcher is separate from the V9/V12.1 fetcher. It tries Binance's public market-data host first (data-api.binance.vision), then the standard Spot and GCP Spot hosts. Each host is paginated backwards in batches of up to 1,000 closed BTCUSDT klines, deduplicated by candle open time, and checked against a minimum requested-history depth of 80% (or 360 candles when the requested limit is lower).

Kraken remains an explicit fallback. Its public OHLC feed is limited to 720 recent candles; when it cannot satisfy the minimum depth, the series is still recorded for diagnostics but marked DEGRADED_DEPTH, with provider attempts and coverage included in the input/report. No missing candles are fabricated or forward-filled. BTCUSDT remains a USDT-quoted proxy, clearly identified in metadata rather than being described as exact BTCUSD.

Official API references:
- Binance public market-data endpoint: https://developers.binance.com/en/docs/products/spot/faqs/market_data_only
- Binance Spot REST API base endpoints and time parameters: https://developers.binance.com/en/docs/products/spot/rest-api
- Kraken OHLC history limit: https://support.kraken.com/in/articles/advanced-api-faq

## HOLD-aware training experiment

V12.2 freezes one context mode per specialist based on V12.1's highest development selection score. This avoids reopening the context search while the experiment isolates four training objectives:

1. Inverse-frequency weighted cross-entropy (V12.1 objective).
2. Inverse-frequency cross-entropy with a fixed 1.25 HOLD class-weight multiplier.
3. Inverse-frequency weighted focal loss with gamma 1.5.
4. HOLD-boosted focal loss with gamma 1.5 and a fixed 1.25 HOLD class-weight multiplier.

The four objectives use identical samples, time splits, model architecture, training budget, scaler fit rows, and one shared matched V9 prediction set per fold. The report adds per-class precision, recall, F1, actual/predicted counts and confusion matrices, so a rise in HOLD recall cannot hide a collapse in SELL/BUY performance.

Context mode is frozen from V12.1's development evidence:
- Strategic: high_coverage
- Flipper: target_only
- Breakout: full_context
- SMC-Pro: target_only
- Ladder-Flip: target_only

The objective is selected on the 70%-85% development window only. If an objective passes the unchanged development guard, it is frozen before a single evaluation on the untouched 85%-100% final window.

## Acceptance gates — unchanged

Balanced accuracy >=0.36, macro-F1 >=0.34, at least 30 final samples, nonzero SELL/HOLD/BUY recall, and a final selection-score improvement >=0.005 over matched V9. The development guard remains the existing quality gate plus development score delta >= -0.01. No gate is relaxed to obtain a pass.

No model weights are persisted, registered, promoted or deployed. Any research-qualified candidate would still need all-timeframe testing, regime-separated walk-forward validation, execution-aware spread/slippage/commission backtesting, and shadow operation before any production discussion.
